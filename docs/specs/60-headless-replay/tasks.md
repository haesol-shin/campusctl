### Panopto SSO popup: live cause (2026-09-26)

On the LMS lecture roster, its external video-provider integration opens a dedicated SSO popup when login is needed. The popup's top-level frame submits a document POST to the provider's login endpoint; the integration closes its own popup after three seconds. Because the popup may begin during trusted LMS login but post after an operation-scoped interceptor is installed, the previously unreviewed external origin latched `policy-blocked` before archive navigation or a file click. The issue affects both fresh and warm profiles, not just headless Chromium. The separate LCMS download-navigation race was fixed without relaxing this SSO boundary.

### Panopto SSO popup: owner decision and verification

- Abort and count only the exact external Panopto document POST in `assignments.sync`, `notices.sync`, `materials.sync`, and `materials.download`; never alter lecture playback SSO
- Check the popup's LMS SSO top frame and lecture-roster opener when Playwright exposes them; otherwise use the exact reviewed external origin, method, login path, document resource type and operation; close only this popup after abort
- Keep other Panopto requests, methods, paths, resource types, and operations fatal; fixture tests exercise these negative boundaries and the popup close
- Full pytest and Ruff gates pass (476 passed, 3 skipped); five isolated fresh-profile headless PDF downloads succeed with a verified 370228-byte `%PDF-1.7` file, five roster SSO popup openings and one guarded SSO POST suppression; other openings complete before interception and do not latch a denial

- A separate full headless materials metadata sync enumerates seven courses and 30 material rows without course failures; its sole SSO popup POST occurs before the guarded phase, so no SSO suppression is counted there

### H4 sync audit (2026-09-26)

Evidence: owner-held sanitized evidence (2026-09-26). Platform: Linux aarch64 (Raspberry Pi), Python 3.12, Playwright 1.63.0. Headless: Playwright-bundled Chromium 153.0.8010.12, launched locally with a persistent profile inside the audit data directory. Headed: the owner's existing Chrome 151.0.7922.173 over CDP with its warm profile. Scope: unfiltered `lectures`, `assignments`, `notices`, `materials` sync of seven enrolled courses into separate fresh data directories, run sequentially at `14303aa` with the capability table enabled only in the audit process.

- Full-record equivalence: headed and headless catalogs match exactly after removing no fields. Lectures 160/160, assignments 6/6, notices 10/10 (including `is_unread`), materials 30/30; identical course sets (7), `enrollment_state` known in both, zero failed courses, zero differing fields per shared entity ID.
- Reliability: 5 of 22 headless domain runs failed with `course-discovery-failed` before any course work (notices 3 of 12, materials 2 of 8, lectures and assignments 1 of 1 each passed); no domain failed more than twice in a row, and each later passed in the same profile. One captured materials failure timed out after 7 seconds waiting for the roster course links; notices failures ended inside its 10-second bounded roster steps about 16 seconds after start, with the exact step not captured. Every failure was the first run after a different domain in the same persistent headless profile; 5 consecutive notices-only runs all passed. Headed CDP runs had no failures (4 of 4).
- Decision: keep every `*.sync` entry `False` in `HEADLESS_SUPPORT`. Enabling requires a roster-wait fix and a new audit with five consecutive clean all-domain headless runs plus the same full-record comparison.
