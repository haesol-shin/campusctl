## Owner decision (2026-09-26)

The per-course notice board is authoritative, not the global to-do grid. For each enrolled course, enter `/std/myLecture` → `POST /api/v1/course/addSessionCourseInfo` → `/std/lecture` → `/std/notice`, and require successful `POST /api/v1/board/notice/list/top` and `POST /api/v1/board/notice/list`. Every board row is a notice, even if absent from `/std/todo`; uniquely matching to-do rows preserve historical timestamp/ordinal identity and supply `status` and `is_unread`, while all other board rows have unknown read state. More than one board page fails that course with `notice-board-paginated` and preserves prior rows as stale. Only a completed own board list response with zero items and zero rendered rows verifies an empty course. Never open `noticeDetail` or call `/api/v1/board/notice/info`.

Optional outside-origin passive GET assets without Range or redirects are aborted and counted as `third-party-asset`. Exact reviewed Panopto SAML, LMS college PNG, LMS favicon icon, and external telemetry POST requests are suppressed, not permitted to load; unknown-origin POST and xhr/fetch/document/other requests remain fatal. Owner decision 3 permits only exact LMS POST `/api/v1/week/getStdActivityStatus` XHR as a read-only `notices.sync` route from `/std/lecture`; aborting it triggers a blocking server-communication modal. All other unsuppressed logging-token requests remain denied. No broad route, media or download allowances follow from this decision. Evidence is the owner-held sanitized LMS board diagnosis and suppression bisection dated 2026-09-26.

## Required behavior

- `sync --only notices [--course ID]` authenticates once, guards every subsequent request, discovers enrolled courses and syncs each selected course independently. Bind each course's session-course selection request and the rendered notice page course identity, the board's main-frame commit, post-commit top/list request sequence, exact `/std/notice` Referer and successful response; reject stale, absent or duplicate responses. A failed course retains all previous rows and gets a stale marker. A filtered sync leaves other courses unchanged. Full discovery failure preserves prior rows/timestamp while marking enrollment unknown; filtered discovery failure changes nothing. A wholly successful full scan may remove unenrolled courses.
- Board pagination uses page size 10. Numeric page beyond one, enabled Next, ordinary-list total above 10 or ordinary-list length below total fails that course; never publish a partial list as complete. Validate both HTTP 200/`header.code:200` top/ordinary response item arrays, their ordinary total, and the deduplicated count against rendered board rows. Zero rows clear stale cache only when both JSON lists and ordinary total are zero. Neither initially empty UI nor `/std/todo` empty state establishes a verified-empty course.
- `notices list [--course ID]` reads the cached catalog without browser, config or lock, showing stale warnings as appropriate. JSON uses the standard versioned envelope and exposes cache enrollment/failures. Human output shows full selectable IDs on separate lines and known unread state only.
- Every row has `entity_id`, `legacy_key`, course ID/label, `kind`, title, date, `status` and `is_unread` (both nullable), author, integer-or-null view count, boolean-or-null attachment presence, nullable `posted_date` and `author_role`. The reviewed `file_yn` numeric 0/1 supplies false/true, and unknown indicators remain null. Never infer author role from a name; do not store contact IDs or phone numbers from source JSON.
- Legacy identity uses course label, displayed date and ordinal number exactly as the read-only legacy notifier parser (owner-held sanitized parser evidence, 2026-09-25) does, including internal date whitespace; entity ID uses course ID plus date/ordinal. Match to-do by native `TB_L_BOARDITEM{digits}` when present; without it, only a unique course/title/date-day pair can preserve the old timestamp and ordinal. Any ambiguous pair fails the course as `notice-identity-ambiguous`, keeping old rows stale. The board response's `insert_dt_addtime` supplies a valid board-only timestamp (`YYYY-MM-DD HH:MM`), falling back to day-only `insert_dt` if unavailable; never fabricate a historical to-do key.
- Notice sync is read-only and metadata-only. No detail requests, attachments, media, mutations or unsanctioned third-party data requests. Headless mode fails before browser launch pending independent approval. Fixture tests never access live LMS.

## Acceptance scenarios

1. Two boards each contain rows; to-do includes only one or none. Both boards' rows are committed and unmatched unread is null.
2. A completed zero-row board clears its old rows; an absent, stale or duplicate board response retains them as stale.
3. A board advertises a second page; its old rows survive and `notice-board-paginated` is reported.
4. A matching native board item in to-do contributes exact legacy displayed timestamp/number and unread true/false without adding global-only rows.
5. No detail URL is ever requested; guarded optional suppressions do not permit forbidden third-party data.
