# v0.4.0 — student-first CLI: specification

[Constitution](../constitution.md) · [Design](design.md) · [Tasks](tasks.md). Understood as: deliver a Windows-student-friendly local CLI and explicit-ID agent API, without broadening LMS authority. This is a planned v0.4.0 contract, not a claim that main already implements it. Source anchors refer to baseline `adb2684`.

## Required behavior

1. **Sync all by default.** `campusctl sync` selects lectures, assignments, notices and materials. `--only lectures,notices` narrows the finite set; strip surrounding whitespace, reject empty/unknown tokens, deduplicate, execute in canonical order `lectures,assignments,notices,materials`. Never interpret `all`, a wildcard, or an empty value as a domain. Single-domain JSON retains its existing result shape; multi-domain JSON uses the design's aggregate. Validate arguments and effective browser support for every selected domain before any work. Metadata only; no downloads, detail fetches or playback. Baseline defaults and one-module dispatch are `src/campusctl/cli.py:96-100,453-473`.
2. **One course resolver.** Human `--course` uses exact ID first, then a positive 1-based index bound to the last successfully printed `courses list` generation, then a unique name substring after Unicode whitespace removal and `casefold()`. Persist the printed roster; changed sources/roster give actionable `selection-stale`/user-action/2 rather than targeting the new occupant of that number. No chosung, fuzzy, or initial-consonant search. Blank normalized selector is invalid. Numeric exact IDs win over indices; out-of-range indices do not fall through to names. In resolved JSON output mode, full IDs are the only accepted selectors: after exact roster lookup fails, numeric input returns `course-index-unavailable`, other input returns `course-id-required`, with remediation to use full IDs from `courses list --json`. Do not infer ID syntax or normalize/match a name in that branch. Human name ambiguity lists full candidate IDs/labels (`course-ambiguous`); human no match returns `course-not-found` and points to `courses list`. All are user-action/2, never empty successful lists. Existing inconsistent filters are `cli.py:489-490`, `providers/cnu/sync.py:59-69` and the domain contracts.
3. **One material per selection.** Human `materials list` prints a stable 1-based number and full ID per row. A number identifies the last successfully printed human materials list, including its filter/order, not a newly sorted catalog. Persist that selection snapshot with the exact catalog generation; any catalog rewrite invalidates it, even within the same timestamp second or with identical rows. `materials download 3` is human-only. An ID remains valid independently of a printed list and still undergoes existing provider revalidation. Bare download opens a numbered single-select picker only when stdin and stdout are terminals and resolved output is human; JSON/non-TTY needs a full ID. Empty/invalid choice never chooses a default. Cancel returns `selection-cancelled`/user-action/2 without browser startup. No bulk download, ranges, comma lists or course-wide download. Baseline single-file binding and receipt checks remain `commands/materials.py:185-203,239-365`.
4. **Visible freshness and explicit refresh.** Every `list`, including `courses list`, displays catalog generation age and an actionable hint when age is strictly greater than six hours (21,600 seconds). Six hours covers a student's morning/afternoon/evening checks without implying real-time monitoring. It is an advisory, not a freshness guarantee or automatic network permission. JSON adds numeric age and flags; keep unknown/failed enrollment warnings even when age is young or a filtered list is empty. `list --refresh` synchronizes that domain, with the resolved course filter, then lists the resulting catalog; `courses list --refresh` synchronizes lectures. It never refreshes unrelated domains. Failed refresh is not disguised as a successful cached response. Baseline lists are local-only (`cli.py:476-504`; domain contracts); without `--refresh` they stay configuration/browser/network independent.
5. **Local status.** `campusctl status [--course SELECTOR] [--json]` reads catalogs only. Show unsubmitted assignments due in `[now, now + 7 days)`, known unread notices with a separate unknown-read count, and incomplete lectures with `open:true`, ordered by nearest future deadline or availability. Include missing, stale, unknown-enrollment and failed-course coverage. Never claim 'nothing to do' when a source is missing/invalid. Use Asia/Seoul for timezone-less LMS dates; do not use the host timezone. Status is not `/std/todo`: owner-observed todo/board notice counts were 0 versus 1 and 1 versus 9; current notices already treat boards as primary and todo only as read-state/identity support (`docs/contracts/notices.md:5-24`; `providers/cnu/notices.py:790-808`). No automatic refresh or new LMS route.
6. **Global browser preference.** Add Boolean `browser.headless` (default false everywhere, including Windows/desktop) and mutually exclusive global `--headless` / `--headed`, before the subcommand: `campusctl --headless sync`. CLI overrides config, config overrides headed default. Remove command-local headless flags, not aliases; old `campusctl sync --headless` is usage-error/2. Unsupported operation-mode pairs fail before browser/catalog mutation, never silently fall back. [60-headless-replay](../60-headless-replay/spec.md) owns evidence gates, including download/playback. Preserve CDP rejection of headless (`browser.py:287-299`). Cached lists/status ignore browser preference and remain usable without config.
7. **Guided setup.** Human dual-TTY `campusctl setup` sequences config creation/reuse, approved Chromium install/check, missing keyring password through hidden `auth set` behavior, `auth status --check`, then optional first full sync (default no). Each stage rechecks durable state, never rewrites existing config/password or reinstalls an available browser. Stop at the first failure/decline with the exact next action; rerun resumes from actual state, not a fabricated progress flag. Command-provider credentials skip password storage and run the helper check. Explain that `auth status --check` checks credentials presence/helper execution, not LMS login (`docs/contracts/cli.md:38,109`). Keep scripting commands; `setup --json` and noninteractive setup retain the browser-only installer contract. Add `setup --browser-only` for an explicit human scripting equivalent. No passwords in arguments, environment, JSON or logs. See existing stages in `setup.py:89-118`, `cli.py:408-452` and `config_init.py`.

## Fetch boundary and compatibility

Assignment/notice detail fetch stays exclusively in [40-fetch](../40-fetch/spec.md). Its full entity IDs are not materials row numbers. Do not add numbers to fetch or a `--course` flag merely because materials gained a picker; the selected ID already identifies its course. All actual `--course` flags use the common resolver. Future fetch browser choice uses the global preference, with its own headless gate. Preserve 40-fetch's unpublished-until-approved rule.

Breaking changes to document at release: bare sync scope; unknown course filters now errors; command-local headless flags removed; interactive setup now guided. Additive JSON remains schema 1. Full entity IDs, errors/status/exit semantics and official selected-file safeguards remain unchanged.

## Acceptance and open evidence

- Human can run setup, full sync, `courses list`, `materials list --course 1`, then `materials download 3`; exactly the printed file is selected or a stale-list error occurs.
- Agent can run `sync --only assignments,notices --json`, `status --course <course-id> --json`, and one full-ID material download without a prompt or stdout contamination.
- After printing a roster, inserting/removing a lower-sorting course or rewriting a contributing generation makes every numeric `--course` consumer fail selection-stale before network; full-ID selection remains independent. JSON rejects both index and unique name fragments across sync, refresh, lists and status, including with no prior printed roster.
- Fixture-first integration proves no network for ordinary list/status, no accidental browser launch on bad selection, and retained stale rows are never labeled refreshed.
- **TBD, evidence not present:** whether todo actually lists assignments or lectures. The owner-held sanitized observation report (2026-09-25, lines 24-29,114-116,157-164) records a todo endpoint and an empty learning container, not populated assignment/lecture rows. UX tasks include an evidence-only follow-up; this cannot change status's catalog source.
