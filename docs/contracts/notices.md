# Notice metadata contract

## Source and completeness

Bare `sync` collects all four domains in one combined pass; `--only notices` narrows it. The pass selects each course once and visits its board through the rendered notice menu. Completed `/api/v1/board/notice/list/top` and `/api/v1/board/notice/list` JSON responses are primary; the committed board route, matching topbar, table body and rendered row IDs must agree with the response items before publication. An empty board is confirmed only by completed empty responses and an empty table. Every nondeleted board item appears even if absent from global `/std/todo`. Matching to-do rows preserve historical identity and supply read state; unmatched items have `is_unread: null`. An incomplete to-do grid leaves affected courses stale rather than silently changing keys. A numeric page beyond 1, enabled Next, ordinary total above 10, or list length below total fails the course as `notice-board-paginated` and retains its previous rows.

The global to-do snapshot waits for its committed document, a completed first list response, and a rendered grid (rows or an explicit empty state). Before accepting each page, its row identities, empty state and enabled Next control must remain unchanged for a short quiet window within the page deadline. It follows the stable Next control until no page remains; the response's list count and total do not define the grid's page size or completeness. Subsequent list responses must complete when present. Stale or duplicate responses, repeated pages, invalid rows, or a page that never settles leave affected courses stale.

The session-course POST carries an opaque encrypted value and can navigate immediately. Course identity comes from the committed page, topbar and board items, not the POST body. The notice board opens via the rendered menu; a direct `/std/notice` navigation can redirect to the home page. Page requests are unfiltered. Notice attachments are recorded as omissions without transfer until an attachment-bearing notice and its approved control are observed. Global `--headless` supports notice sync with local Chromium. Notice fetch local headless is an unreleased candidate pending the next live run; CDP headless returns `headless-unavailable`.

## Commands

```text
campusctl sync --only notices [--course COURSE_ID] [--json]
campusctl notices list [--course COURSE_ID] [--refresh] [--json]
campusctl [--headless|--headed] notices fetch ENTITY_ID... [--out DIR] [--json]
```

`list` reads `<data-dir>/catalog/notices.json` without network, configuration, browser or lock; `--refresh` first syncs this domain. Human `--course` accepts exact ID, last-printed course number or unique name fragment; JSON requires exact ID. Unknown filters return `course-not-found`. A sync result reports freshly committed `courses`, `notices`, `failed_courses`, catalog timestamp and enrollment state. Failed courses retain old rows while other courses and domains continue. Full discovery failure preserves prior rows/timestamp and marks enrollment unknown; filtered failure leaves unrelated rows untouched. Errors name the failed domain and step.

## Row fields and identity

Each `result.notices[]` row has `entity_id`, `legacy_key`, `course:{id,label}`, `kind:"notice"`, `title`, `date`, `status`, `is_unread`, `posted_date`, `author_role`, `author`, `view_count`, and `has_attachments`. The board response's `writeruser_name` becomes author, never an inferred author role. `boarditem_viewcnt` becomes an integer or `null`; reviewed numeric `file_yn` 0/1 becomes false/true (other or absent indicators remain `null`). `insert_dt` is a displayed day, while `insert_dt_addtime` supplies a date and time. Posting date and author role remain `null` unless separately observed. Unread is true/false only when a matching to-do row says `읽지않음`/`읽음`; otherwise `null`. Personal/contact response fields `writeruser_phone`, `writeruserno`, and `ref_user_no` never enter the catalog or output.

The legacy parser uses the trimmed displayed course label, date and ordinal number: `<label>_<date>_<number>`, preserving internal date whitespace. A native-ID match or a uniquely matching course/title/date-day row without a native ID supplies the original to-do timestamp and ordinal for byte-compatible `legacy_key` and `entity_id`. Ambiguous matches fail that course as `notice-identity-ambiguous`, retaining its old rows. The board DOM displays `insert_dt` (`YYYY-MM-DD`), but its observed `insert_dt_addtime` is `YYYY-MM-DD HH:MM`, which supplies the board-only identity date when valid; otherwise the displayed day is used. A board-only notice has no pre-existing to-do key to preserve. The native `TB_L_BOARDITEM{digits}` is a join key, not a substitute public identity. Treat the opaque entity ID as indivisible.

## Human and error output

The human list shows the course, title, displayed date, known read state only, author, view count, attachment presence and full untruncated ID on its own line. Unknown metadata is labeled `unknown`; unknown unread is not mislabeled read. Unknown enrollment and failed courses print stale warnings, including on an empty filtered list. JSON exposes `cache.generated_at`, `cache.enrollment_state`, `cache.failed_courses`, and all rows within the standard `{schema_version,tool,tool_version,status,result,errors,generated_at}` envelope. Errors use safe `{code,message,remediation}` with the failing domain and step, without raw LMS bodies or URLs. `notice-board-paginated`, `notice-identity-ambiguous`, `item-identity-missing` and `course-sync-failed` are partial sync errors; `headless-unavailable` and `course-not-found` require user action.

## Selected detail fetch

`fetch` accepts one or more explicit full notice entity IDs from the matching cached list, deduplicated in first-seen order. Numbers, title guesses, globs and `--course` are not accepted. A missing or stale ID fails before browser startup. One distinct ID returns `result.source_package`. More than one returns `result.items` and uses one session for the ordered queue. It opens each selected course board through the ordinary menu, verifies the selected notice against its detail response, and packages readable text. Opening a detail can increment its view count and may change its read state as ordinary reading; fetch does not click mark-read and does not retry a detail. Refresh the notice list to check the current state. Local headed and headless notice fetch are an unreleased candidate pending the next live run. CDP headless returns `headless-unavailable` before startup. It holds the non-blocking session lock.

The selected fetch waits for the board's two completed list responses and matching rendered links before clicking the unique notice. The detail URL and completed info/comments responses must identify that notice and course before content packaging; unrelated images need not finish.

By default, a package lives under `<data-dir>/sources/notice/<sha256-of-entity-id>/<package-digest>/`; `--out DIR` instead chooses a **nonexistent package directory** and never overwrites. The directory contains `package.json`, `content.md` and any included `images/`. The manifest records selected ID, kind, course, query-free source reference, retrieval time, content path, completeness and included/omitted resources. Included resources have deterministic IDs, normalized source references, media type, size and SHA-256; omissions record IDs and reasons. Notice attachments are **always omitted** as `unverified-notice-attachment`, never transferred; external, media and unsupported references are likewise omitted. A transfer or identity failure publishes no package. An identical default package may be reused after verification.

One distinct ID returns `result.source_package` with `entity_id`, `completeness`, absolute `path`, `manifest_path`, `content_path`, included `resources` (absolute paths), `omitted_resources`, and `provenance` (`provider`, `course_id`, `source_ref`, `retrieved_at`) in the [standard envelope](cli.md). Human output for that ID prints `Notice source`, `Package`, `Content`, `Completeness`, and one `Omitted` line per skipped reference. Complete single packages return `ok`/0; omissions return `partial`/1 with `resource-omitted` and the usable package. A multi-ID request is `ok`/0 only when every item is `completed`; any published package with a partial, failed or not-started item is `partial`/1; otherwise the envelope uses the first failure's status and keeps every item and ordered error. Missing/invalid catalog, unknown ID, output conflict, CDP headless or login action return `user-action`/2; operational detail/transfer failures return `error`/1; session lock contention returns `busy`/75. Errors name the failing fetch step without raw response data.
